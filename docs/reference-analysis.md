# 米奇妙妙屋 EXE：窗口透明度实现分析

分析日期：2026-10-14。仅检查 PE、Delphi 窗体资源、方法表及反汇编调用关系，未运行参考程序，未修改目标窗口或参考文件。

## 结论

该程序采用“直接修改窗口透明度，失败时嵌入自建父窗容器”的混合方案。容器分支会改变目标窗口的父子关系，将后续透明度操作转向容器窗口。

未发现专门在第三方窗口重新显示后恢复透明度的业务路径。不能仅凭容器分支存在，就断言钉钉实际使用了该分支，或参考程序已经解决了钉钉清除透明样式的问题。

## 1. 普通透明度路径

主窗滑块事件 `TfrmMain.trbTransChange` 位于 `0x481708`，在 `0x481753` 调用透明度函数 `0x46C480`。

该函数依次执行：

1. `GetWindowLongA(hwnd, GWL_EXSTYLE)`
2. 为扩展样式增加 `WS_EX_LAYERED`，然后 `SetWindowLongA`
3. `SetLayeredWindowAttributes(hwnd, 0, alpha, LWA_ALPHA)`，调用位置 `0x46C4AC`

滑块位置被换算为 `alpha = 255 - TrackBar.Position`。这是标准的窗口整体透明度设置，没有在这个函数内启动后台恢复任务。

## 2. 直接设置失败后：父窗容器

`trbTransChange` 在 `0x481758` 检查透明度函数返回值。成功时直接更新列表；失败时检查 `GetParent(target)`，并进入已有容器查找或新容器创建分支。

新容器路径的主要证据：

| 地址 | 行为 |
| --- | --- |
| `0x4817D3` | 创建 `TfrmParent` |
| `0x4817E0` | 调用 `0x48098C`，传入原目标窗口 |
| `0x4809BA` | 获取并保存目标原父窗口 |
| `0x4809E4` | `SetParent(target, container)`，将原窗口挂到自建窗体下 |
| `0x480A04`、`0x480A25` | `MoveWindow`，调整原窗口和容器的位置、尺寸 |
| `0x4817F5` | 把当前调整目标替换成容器 HWND |
| `0x481819` | 记录容器与原目标的对应关系 |
| `0x480AA9`、`0x480AC6` | 容器关闭或销毁时，通过 `SetParent` 恢复原父窗口 |

容器还同步原窗口标题和图标，并通过 `SetParent` 改变真实窗口层级。

从滑块事件的分支可以确认：新建容器后会先替换当前目标；创建分支内没有第二次调用透明度函数。后续滑块变化再走同一事件时，操作的对象已经是容器。

完整解析主窗和容器的 DFM 后，未发现强制启用容器模式的设置，主窗唯一复选框为 `chkStayOnTop`。容器资源没有预设 `AlphaBlend` / `AlphaBlendValue` 属性，`FormCreate` 也未设置 alpha。因此，不能把容器创建本身描述成已经立即应用了所选透明度。

容器分支的简化流程如下，省略列表更新和异常处理：

```text
滑块变化
  → 对当前 HWND 设置透明度
  → 成功：更新记录
  → 失败：检查 GetParent 和已有容器记录
      → 条件满足时创建容器
      → SetParent(原窗口, 容器)
      → 当前 HWND 改为容器 HWND
      → 后续滑块变化调整容器
```

## 3. 定时器和 Hook 的用途

两个业务定时器均属于 `TfrmParent`，不是主窗透明度维护任务：

| 定时器 | 方法地址 | 间隔 | 实际用途 |
| --- | --- | --- | --- |
| `Timer1` | `0x480BA0` | 500 ms | 停用自身，从命令行参数取得目标 HWND，建立容器关联，再启用 Timer2 |
| `Timer2` | `0x480C1C` | 5000 ms | 检查原目标 `IsWindow`，失效则关闭容器，否则同步窗口标题 |

这些定时器内没有调用透明度设置函数。

`SetWindowsHookExA` 的唯一调用位于 `0x459CC8`，参数是 `WH_GETMESSAGE`、本进程当前线程 ID。回调 `0x459C5C` 经 VCL Application 调用 `THintWindow` 的消息判断，最终在 `0x45C1CC` 隐藏悬停提示窗。类名和 VMT 对应关系也已核对，因此可以确认这处 Hook 用于本程序提示管理，不是监视钉钉窗口的跨进程 Hook。

导入表和名称字符串中未发现 `SetWinEventHook`、`UnhookWinEvent` 或 `GetLayeredWindowAttributes`。这是静态扫描范围内的未发现结果，不能据此排除所有可能的动态 API 调用。

## 4. 对钉钉透明度重置问题的含义

需要区分两种失败：

- **首次设置就失败**：样本的容器分支可能介入，让后续透明度作用在自己创建的窗体上
- **首次设置成功，钉钉重新显示后清除透明样式**：上述失败分支不会因此自动触发；已发现的定时器和 Hook 也没有透明度补写逻辑

将透明度放到独立容器上，结构上可以隔离“原窗口重置自身扩展样式”对容器透明样式的影响。这是根据窗口层级和调用关系作出的推断，尚未验证钉钉在这个容器中的重新显示、激活、移动和关闭表现。

因此，该样本提供了一种容器思路，但没有足够证据把它当作已验证的钉钉重置修复。采用该方案会涉及目标父子关系和位置调整，不能等同于替换一个透明度 API。本次只完成分析，没有把容器方案加入 Trans。
